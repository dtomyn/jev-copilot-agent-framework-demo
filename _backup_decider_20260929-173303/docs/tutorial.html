Typed AI decisions for agents: Jev and Laya in ten levels

This project demonstrates one idea: a coding agent does not need to use a general-purpose language model for every judgment. Small, bounded decisions can be handed to a fast decision engine, returned as typed values, and then interpreted by ordinary code.

.NET 10 TypeSafe Jev Laya GitHub Copilot CLI Microsoft Agent Framework mock-first demo
If you only remember one sentence

The decision model supplies evidence; your code owns the action. Jev or Laya can say “this looks risky” or “this belongs in the ask bucket.” They do not get final authority to run a command, edit a file, or approve themselves.

The progression was inspired by the “levels” style of the original Jev demo: start with one tiny judgment, then keep the same primitive while moving it closer to a real agent workflow. This version also lets you switch between TypeSafe Jev, a hosted System One model, and Laya, an open-source local decision engine that can speak the same POST /v1/systemone contract.

Inspired by the video, not a line-for-line port

The original “10 Levels of Jev” video supplies the learning shape: begin with cheap bounded judgments and end with agents that know how to use them. This repository adapts that idea to a .NET + GitHub Copilot safety workflow, so its level names and examples intentionally differ.

How to read this tutorial

The first few sections explain the whole demo without assuming you know Jev, Laya, agent hooks, or confidence gating. Then the ten levels add one idea at a time. The “Presenter note” blocks are also shown inside the running web application, so they are written as self-contained explanations, not private speaker notes.

The 60-second mental model

Every example in this repository can be reduced to the same five-step loop:

1
Give the engine some stateThe text or structured context you want judged: a proposed command, a ticket, a code-change description, and so on.
2
Ask a bounded questionYes/no probability, one choice from a list, or a position on an ordered rubric.
3
Receive a typed answerA number or label plus probabilities. No prose needs to be parsed.
4
Apply policy in codeYour C# decides thresholds, hard rules, fallbacks, and what uncertainty means.
5
Act, ask, or stopThe surrounding application chooses the real-world outcome.

Good fit

“Is this destructive?” “Which route fits?” “How risky is this on four defined levels?” These are narrow judgments with a known answer shape.

Not the job

Writing the feature, planning an open-ended migration, browsing a UI, or running a shell command. The decision engine is a small primitive beside the agent, not a replacement for it.

Do not confuse “typed” with “guaranteed correct”

A typed answer is easier for software to consume, but it is still a model judgment. That is why this demo keeps deterministic rules for obvious hazards, uses confidence thresholds for the fuzzy middle, and sends uncertainty to a human instead of silently turning it into permission.

What the ten levels add

LevelsQuestion they answerNew idea
1-4What can a typed decision engine return?Noul, Choice, Score, then several questions over the same state.
5Who is actually in charge?Deterministic rules and C# thresholds turn model evidence into policy.
6-7Can an agent use this as a tool?Expose one decision primitive, then the whole typed toolbelt, through Microsoft Agent Framework.
8-9Can the same policy guard real tool calls?Wire the gate into Copilot CLI preToolUse, with human escalation for ambiguity.
10Can the agent decide when this primitive is useful?The agent chooses whether to call Jev/Laya for a bounded subproblem instead of being told every time.

The important progression is not “more AI.” It is better placement of a small decision primitive.

The three typed questions

You only need three concepts before starting Level 1.

PrimitivePlain-English questionUse it when...Result
Noul“Is this statement true?”You want a yes/no judgment with a probability.A number from 0 to 1: probability of “yes.”
Choice“Which of these named options fits best?”The answer must be one label from a known set.The selected label plus probabilities for the options.
Score“Where does this fall on this ordered scale?”The answer has an order: low → medium → high, safe → dangerous, etc.A score over the rubric plus its distribution.

A useful rule of thumb: if you cannot describe the answer shape before the model runs, the question is probably too open-ended for this primitive. Break it into smaller judgments or let the agent/ordinary code handle it another way.

Presenter note

Levels 1-4 are about answer shapes, not agents. The state is ordinary text and the model returns typed evidence. Nothing is executing a shell command or editing a repository yet.

The most important habit is to make each question narrow. Ask one semantic thing, get one typed answer, then compose several answers in code when the real decision has multiple dimensions.

The ten levels, one idea at a time

Level 01 - the smart if-statement Run live

Scenario: Copilot proposes rm -rf ./artifacts after a build. The application asks one Noul question: “Is this proposed coding-agent action potentially destructive?”

run it
dotnet run --project src/TenLevels.Jev -- --level 1 --mode mock

The model returns a probability. Then ordinary C# compares that number with 0.80 and chooses either BLOCK or “continue normal checks.” The threshold is application policy; it is not hidden inside the model prompt.

Presenter note

What to notice: the AI part ends at a number. The branch is normal C#. That separation is the core pattern for the rest of the demo.

Try editing the state until the probability moves across the threshold. You are not asking the model for permission; you are deciding what probability is enough for your code to take the next step.

Level 02 - typed routing Run live

Scenario: Copilot wants to install a global CLI package and update PATH. A boolean would be too crude, so the application gives the model three explicit routes: allow ask deny.

run it
dotnet run --project src/TenLevels.Jev -- --level 2 --mode mock

The useful part is the bounded vocabulary. Downstream code does not need to parse sentences like “this seems a little risky.” It receives one of three known labels and the probability distribution behind it.

Presenter note

Choice is semantic routing. You define the buckets before inference, including what each bucket means. The model selects among your options instead of inventing a new category.

This is a good fit for triage, intent routing, queue selection, or any workflow where the next branch is already known in code.

Level 03 - ordered risk Run live

Scenario: Copilot proposes edits across several source files plus a package reference. The application wants more than a category: it wants a position on an ordered risk scale.

the rubric
0  Read-only or trivial reversible action
1  Repository-local mutation with easy rollback
2  Broad change affecting dependencies, generated assets, or repository state
3  Destructive, system-wide, credential-sensitive, or difficult to reverse
run it
dotnet run --project src/TenLevels.Jev -- --level 3 --mode mock
Presenter note

Score is for ordered meaning. The four descriptions are not just four unrelated labels; moving right means “more risk.” That lets the engine place an ambiguous example between neighboring levels.

Write rubrics in concrete language. “Good / okay / bad” gives the model much less to work with than descriptions tied to reversibility, scope, credentials, or other observable properties.

Level 04 - parallel typed judgments Run live

Scenario: Copilot wants to run tests and then commit generated snapshot changes. One state is useful to several questions, so the request asks all three primitives together:

  • Noul: are there persistent side effects?
  • Choice: should this be allow / ask / deny?
  • Score: where is it on the risk rubric?
run it
dotnet run --project src/TenLevels.Jev -- --level 4 --mode mock

This is the first point where the system starts to feel like a small decision service instead of a single classifier. The questions remain independent and typed; your code decides whether and how to combine them.

Presenter note

Do not replace one giant prompt with one giant typed question. Ask the smallest questions that matter. If the real policy depends on side effects, route, and risk, keep those as separate signals so you can inspect and reweight them independently.

Level 4 is also the best provider smoke test because it exercises Noul, Choice, and Score in one call.

Level 05 - code owns the policy Run live

Now the demo stops treating the model answer as the whole decision. CopilotToolGate wraps model judgment in deterministic policy.

1
Hard denyKnown destructive command patterns stop immediately. No model call.
2
Sensitive-data checkSecret-shaped input becomes ask and is not forwarded to the model.
3
Read-only / decision-tool fast pathsKnown non-mutating tools can pass without spending a model call.
4
No providerIf no decision engine is configured, mutations escalate to a human.
5
Bounded model judgmentOnly the ambiguous middle reaches Jev/Laya; C# then applies the thresholds.
run it
dotnet run --project src/TenLevels.Jev -- --level 5 --mode mock

The sample compares three cases: a read-only file view, a package mutation, and a force push. They are intentionally decided by different layers so you can see that “the gate” is more than a model call.

Presenter note

This is the architectural turning point. The safe design is not “ask a model if the command is safe.” It is “use deterministic rules where the answer is already known, use a model only for the fuzzy middle, and keep the final thresholds in code.”

That gives you something you can test and audit. A hard-deny regex, an allow threshold, and an escalation path are all visible policy. A prose model answer by itself is not.

Level 06 - the decision engine becomes a Copilot tool Run live

So far the application chose when to call the decision engine. Level 6 exposes one narrow Noul function to a Copilot-backed agent through Microsoft Agent Framework.

Scenario: a pull request changes authentication middleware and token-refresh code. The agent is told to ask Jev/Laya whether security-focused review is warranted, then apply a code-owned 0.70 threshold.

full agent run (requires authenticated Copilot)
dotnet run --project src/TenLevels.Jev -- --level 6 --mode mock
Presenter note

The agent is not being replaced. Copilot still interprets the task and communicates with the user. The decision engine is one specialized function tool it can call for a narrow probability.

The web UI can call that function tool directly without starting Copilot. Use the full-agent button only when you want to demonstrate the orchestration layer too.

Level 07 - Copilot gets the decision toolbelt Run live

Level 7 exposes Noul, Choice, and Score together. The agent can compose the same primitives you used manually in Levels 1-4.

Scenario: “Upgrade a logging package, regenerate snapshots, and commit the result.” The agent uses a Choice for allow/ask/deny and a Score for operational risk, then summarizes both without changing files.

full agent run
dotnet run --project src/TenLevels.Jev -- --level 7 --mode mock
Presenter note

Give the agent primitives, not authority. The tools return typed judgments. They do not expose shell or file mutation. That keeps this example focused on composition instead of quietly creating a second execution surface.

A good agent instruction also says when not to call the model: arithmetic, exact facts, and deterministic repository inspection should stay deterministic.

Level 08 - native Copilot preToolUse hook Run live

Now the same gate moves into Copilot CLI's real tool lifecycle. Before a proposed tool runs, Copilot passes its name and arguments to the checked-in repository hook.

where the hook is registered
.github/hooks/jev-policy.json
        │
        ▼
src/Jev.CopilotHook/Program.cs
        │
        ▼
CopilotToolGate.EvaluateAsync(...)

The web UI starts the real hook executable as a child process, feeds it a real preToolUse payload, and shows the raw stdout, exit code, and expected decision.

Presenter note

Level 8 is integration, not new intelligence. The policy from Level 5 is reused. What changes is where it sits: now it runs at the moment Copilot is about to use a tool.

The adapter has a strict contract: exactly one JSON object on stdout and exit code 0. It also enforces its own shorter deadline so a slow or failed provider degrades to an explicit human approval rather than silently becoming permission.

Level 09 - confidence-aware human escalation Run live

A production-friendly gate needs more than “allow or deny.” Level 9 makes ask a first-class outcome.

OutcomeMeaning in this demo
allowA deterministic safe path or a high-confidence low-risk model result clears the code-owned threshold.
askThe action is ambiguous, potentially consequential, the provider is missing/failed, or confidence is insufficient. A person decides.
denyA hard hazard matched, or the bounded model result clears the deny policy.
run it
dotnet run --project src/TenLevels.Jev -- --level 9 --mode mock
Presenter note

Uncertainty should change behavior. The useful feature is not merely that the model has a confidence number; it is that the application has an explicit policy for what to do when the number is not enough.

In this repository, “not sure” means ask a human. Provider errors and timeouts take the same conservative path. They do not become implicit allow.

Level 10 - the agent reaches for the engine itself Run live

At the last level, the agent is not told “call Noul now.” It receives the decision toolbelt plus a simple rule: use it when a subproblem is a bounded yes/no, one-of-N, or ordered-score judgment.

Scenario: a developer asks whether the entire test suite should run for a narrowly described serializer change. Copilot decides whether a typed decision is useful, formulates the question if so, and preserves uncertainty in its answer.

full agent run
dotnet run --project src/TenLevels.Jev -- --level 10 --mode mock
Presenter note

This is “agentic Jev/Laya” in the useful sense: the agent knows the primitive exists and chooses it for the kind of subproblem it fits. The engine still does not plan, edit, browse, or execute.

The mature pattern is a toolbox of different capabilities: deterministic code for exact rules, a fast typed model for bounded judgments, and an agent/LLM for open-ended reasoning and action.

Deep dive: how the gate really decides

The layer order in CopilotToolGate is itself the security policy. Reading it top to bottom is more useful than memorizing any one model threshold.

StageWhat happensWhy it is there
HardDenyAnchored deterministic patterns catch known destructive commands.Obvious hazards should not depend on probabilistic judgment.
SensitivePotential credential material becomes ask and is not sent to a provider.Do not leak the thing you are trying to protect while classifying it.
ReadOnlyToolKnown read-only tools are allowed immediately.Avoid latency/cost for decisions the host already knows.
DecisionToolThe repo's Jev/Laya decision functions are allowed after the earlier checks.They return judgments and cannot mutate the machine.
NoProviderRemaining mutations become ask.Missing intelligence must not widen permissions.
ModelJev/Laya classifies allow/ask/deny, then C# applies explicit thresholds.Use semantic judgment only for the ambiguous middle.

The current model thresholds are intentionally visible in code:

  • Deny when deny probability is at least 0.55, or the selected answer is deny with answer confidence at least 0.60.
  • Allow only when allow probability is at least 0.85 and answer confidence is at least 0.75.
  • Ask for everything in between.
Those numbers are demo policy, not universal safety defaults

They exist to make the mechanism concrete. If you adapt this pattern, tune and validate your thresholds on your own labeled decisions, costs of error, and threat model.

Deep dive: how the real Copilot hook fits

Copilot CLI sends a proposed tool call to the hook before execution. The adapter normalizes tool names, asks the gate for a result, and prints one of three decisions:

stdout contract
{
  "permissionDecision": "allow | ask | deny",
  "permissionDecisionReason": "one human-readable sentence"
}

To run a real mock-backed Copilot session, choose the hook mode before starting Copilot CLI:

macOS / Linux
export DECISION_MODE=mock
copilot
Windows PowerShell
$env:DECISION_MODE = "mock"
copilot

Try three kinds of request: read a file, make an ordinary repository edit, and propose an obviously hazardous command. The point is not to memorize the outcomes; it is to watch different policy layers fire.

Jev and Laya: same demo contract, different deployment

The repository intentionally keeps provider differences out of policy code. Both providers answer the same three primitives over the same request/response shape, so the levels and the gate use one client interface.

TypeSafe JevLaya
Where it runsHosted TypeSafe serviceYour local/self-hosted process or container
Endpoint in this repohttps://api.typesafe.ai/v1/systemonehttp://127.0.0.1:8010/v1/systemone by default
AuthenticationTYPESAFE_API_KEYNone by default; optional LAYA_API_KEY
Model selectionjev-latest by defaultThe Laya router chooses a checkpoint unless LAYA_MODEL pins one
Best demo reasonShow the hosted Jev serviceShow the same typed workflow locally without sending the state to a hosted provider
One field is intentionally not treated as portable policy: confidence

Jev and Laya define their provider-native confidence values differently. This gate therefore thresholds on AnswerConfidence, the probability of the reported answer (max(p)), instead of copying a provider-specific confidence threshold across engines.

That distinction is pinned by self-tests: policy reads AnswerConfidence, so a provider switch cannot change a gate decision merely because the provider-native confidence formula is different. Live models can still produce different probability distributions, so provider changes still deserve normal validation.

Presenter note

Provider portability requires choosing a portable signal. Both engines return useful confidence information, but the field called confidence does not have the same formula. The gate uses answer probability for policy and keeps provider-native confidence for display/diagnostics.

Run Laya locally

If you want to replace the deterministic mock with a real local model, the repository scripts expect an upstream Laya checkout and Docker. The Laya checkout is deliberately not vendored into this repository, so first-time setup is a separate concern from running the demo.

First time running Laya?

laya-up expects a LAYA_HOME directory containing a docker-compose.yml and the upstream laya/ checkout. See docs/LAYA.md for the layout and provider details, and the upstream Laya repository for its current install/Docker options. Once that one-time setup exists, the normal demo path is:

Reference: what “mock” means

The mock is not pretending to be a benchmark of Jev or Laya. It is a deterministic implementation of the same interface so the tutorial, gate, hook, and UI can be exercised without credentials or a running model. Use it to learn the architecture and test integration; use live mode and your own labeled cases to evaluate a real provider.

Troubleshooting

The UI says port 5088 is in use

An earlier UI process may still be running. Use --restart or -Restart; the script only stops a process it can identify as Jev.WebUi.

Levels 6, 7, or 10 will not build

Those levels depend on the Copilot runtime and its npm download. The UI, hook, tests, and Levels 1-5/8/9 are intentionally kept usable without that dependency.

Laya live mode is disabled

Start the UI with --laya/-Laya, or set LAYA_BASE_URL before starting it. An already-running UI does not inherit new environment variables.

The hook asks instead of deciding

That can be correct. Missing providers, possible secrets, timeouts, errors, and uncertain model results are intentionally routed to human approval.

Every Copilot tool is denied on Windows

Check the repository hook wrapper and execution policy. The checked-in hook entry uses -ExecutionPolicy Bypass -File so an unsigned PowerShell script can run.

Jev and Laya show different confidence

Expected. Their provider-native formulas differ. Compare the answer distribution and AnswerConfidence when reasoning about this gate's thresholds.

Before adapting this to production

This repository is a teaching demo, not a finished authorization system. If you carry the pattern into production, keep the separation of responsibilities and validate each layer independently.

  • Build a labeled test set from your real tool calls and failure costs.
  • Keep catastrophic cases in deterministic policy when you can state them exactly.
  • Tune allow/deny thresholds on your own data; make ask the natural home for ambiguity.
  • Test rules in both directions: a dangerous input that must match and a benign look-alike that must not.
  • Keep credentials and sensitive content out of external model calls unless your data policy explicitly allows them.
  • Log the stage that decided, the probability distribution used, and the final code-owned action.
  • Decide deliberately what provider failure, timeout, and saturation mean. In this hook they become human approval.
  • Re-validate when you change model/checkpoint, question wording, options, or thresholds.
A decision model is not a security boundary by itself

The valuable pattern here is the combination: deterministic constraints + bounded model judgment + explicit thresholds + human escalation + tests. Do not collapse that back into “the AI said it was safe.”
