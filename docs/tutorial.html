The mental model: the model advises, code authorizes

A System-One decision engine answers bounded semantic questions very fast: a yes/no probability, a one-of-N choice, or a position on an ordered rubric. It is deliberately not a planner and not a code generator. Three providers are supported here and are interchangeable: the hosted TypeSafe Jev API, Laya, and Decider. The two open-source providers run locally and all three speak the same wire protocol. Step 11 installs Laya from scratch; docs/DECIDER.md shows the Windows/Docker Decider path; step 12 proves the provider switch changes no policy decision.

This repository takes that primitive and walks it up ten levels until it is sitting inside a real GitHub Copilot CLI preToolUse hook, deciding whether the coding agent's next tool call should run. One idea holds the whole progression together:

Jev advises; code authorizes.

Jev never returns an authorization. It returns evidence: a number and a confidence. Deterministic C# owns the hard rules, owns the thresholds, and owns the final allow ask deny.

Presenter note

Open with this, because every level after it is a variation on the same idea. Ask the room how they would build a safety check for a coding agent. Most people land on "ask the model whether the command is safe, and run it if the answer is yes."

That design has two problems. Anyone who can get text into the tool arguments can argue with the model, which is prompt injection by another name. And when it lets something bad through, there is no policy to read afterwards, only a prompt.

This repository turns it around. Before Jev sees anything, an anchored regex layer denies the commands nobody needs a model to judge, and a credential layer stops secret-shaped text from leaving the machine. Jev only ever sees the ambiguous middle, and even then the C# code decides what its numbers mean.

If you want one idea to leave them with, it is this. The rules have a miss rate you can measure and test; the model's miss rate is unknown. So the rules go where a miss would be a disaster, and the model goes where the worst it can do is cause one extra approval prompt.

Presenter note

This one is for you rather than the room. Read it before anyone tries the repository on their own machine, because both of these failures are baffling the first time you hit them.

NuGet feeds. NuGet.config clears every source and pins exactly one, nuget.org, and the repository uses Central Package Management. If a machine-level or corporate feed leaks in, NuGet raises NU1507 ("there are N package sources defined"). Directory.Build.props sets TreatWarningsAsErrors, so that warning becomes a broken build. Nothing else in the repository needs a network endpoint outside NuGet, so if someone's build seems to hang, this is almost always why. The repository caps the download at 90 seconds (CopilotCliDownloadTimeout) instead of the SDK's default of 600, so a blocked corporate network produces an error in a minute and a half instead of ten silent minutes.

Presenter note

This step looks like housekeeping, and mostly it is. Two decisions are hidden in it, though, and each is worth a sentence out loud.

The first is the order. Everything that can be built and checked offline goes first. The one project that needs something outside NuGet goes last, and if it fails, the script prints a warning and carries on. Someone on a restricted network still walks away with a working hook, passing self-tests, and a web UI that runs every level that does not need Copilot.

The second is that the hook never builds anything. A preToolUse hook runs on every tool call in a Copilot session, with an 8-second timeout. A cold dotnet build would blow straight through that, and when a hook times out, Copilot CLI fails open. So compiling ahead of time and running a DLL is a security decision as much as a speed one.

Point at what happens when the DLL is missing, too. The wrapper answers ask. It does not answer allow, and it does not crash. The audience will see the same pattern all the way through: whenever something is degraded, the answer falls back to asking a person.

2The three primitives and the wire format

Before running anything, look at the shape of a request. One state, an optional model, and a named dictionary of typed questions. You can ask several questions of different types about the same state in a single round trip.

Three engines answer this exact request: hosted TypeSafe Jev, open-source Laya, and open-source Decider. Both local servers implement the same POST /v1/systemone contract on purpose. Pick one with --provider; everything else in this tutorial is identical. Step 11 installs Laya locally, docs/DECIDER.md covers Decider, and step 12 compares the provider semantics side by side.

POST https://api.typesafe.ai/v1/systemone
{
  "state": "Copilot wants to update a package and regenerate snapshots.",
  "model": "jev-latest",
  "questions": {
    "side_effect": {
      "type": "noul",
      "instructions": "Does this have persistent side effects?"
    },
    "route": {
      "type": "choice",
      "instructions": "How should this be handled?",
      "criteria": {
        "allow": "Low-risk and reversible",
        "ask":   "Consequential or ambiguous",
        "deny":  "Clearly prohibited"
      }
    },
    "risk": {
      "type": "score",
      "instructions": "Rate operational risk",
      "criteria": ["read-only", "small mutation", "broad mutation", "destructive"]
    }
  }
}
PrimitiveQuestion shapeAnswer shapeUse it when
Noul One yes/no proposition, optional true / false criteria noul: probability 0.0 to 1.0 The answer is a single proposition and you want a threshold in code
Choice A named set of options, each with a description choice, confidence, full probabilities map The complete answer space can be written down in advance
Score An ordered array of descriptive levels, index 0 upward score, confidence, legend, probabilities The answer is a position on a rubric, not a category

In C# these map to records in src/Jev.Core/Models.cs, with a polymorphic type discriminator:

src/Jev.Core/Models.cs
[JsonPolymorphic(TypeDiscriminatorPropertyName = "type")]
[JsonDerivedType(typeof(NoulQuestion),   "noul")]
[JsonDerivedType(typeof(ChoiceQuestion), "choice")]
[JsonDerivedType(typeof(ScoreQuestion),  "score")]
public abstract record JevQuestion;

Every implementation talks to one interface, which is what makes the mock and the live client interchangeable everywhere in the repo:

src/Jev.Core/IJevClient.cs
public interface IJevClient
{
    Task<SystemOneResponse> DecideAsync(
        object state,
        IReadOnlyDictionary<string, JevQuestion> questions,
        CancellationToken cancellationToken = default);
}
Presenter note

Before you run anything, put the request on screen and give people a moment to read it. Levels 1 to 4 are all variations on this one shape, so a minute here saves five later. There are three things to draw out.

The rubric is written out in words. A Score takes an ordered list of descriptive levels instead of "rate this from 1 to 10", because a bare number scale means something slightly different to everyone who reads it. When the levels say "read-only", "small repository-local mutation", "broad or stateful mutation", and "destructive or security-sensitive", a reviewer can disagree with the wording of level 2 in a pull request. Nobody can usefully review "rate it 1 to 10".

You get the whole distribution back. A Choice answer carries a probability for every option, not only the winner. CopilotToolGate relies on that: it reads probabilities["deny"] directly instead of trusting whichever option came top. A 0.45 / 0.45 / 0.10 split still has a winner, but it is a coin flip, and code that only looks at choice cannot tell it apart from a 0.95 landslide.

The interface is one method. One state, a dictionary of questions, one call. That is why MockJevClient and SystemOneHttpClient swap with a single command-line flag, and why the self-tests can check the exact JSON on the wire against a stub HttpMessageHandler with no network at all.

Presenter note

Take this one slowly. It is the smallest example in the talk on purpose: one question, one number, one if. Everything that follows builds on this shape without changing it.

Put the cursor on the last line of the source. The 0.80 is a literal in a C# file. It shows up in a diff, it can carry a comment explaining why it is 0.80 and not 0.65, and you can change it without going anywhere near a prompt. Jev supplied the number. The code decided what the number means.

Then scroll up to the NoulCriteria pair. Writing down what "true" means and what "false" means is what turns a vague question into a bounded one. Without it, you are hoping the model and the reader agree on what "destructive" means.

If someone asks why the mock always says exactly 0.94: the state contains rm -rf, which matches a hard-deny regex, so RiskHeuristics.Classify puts it in the High band, and the mock maps High to 0.94 every time. That predictability is what you want in a demo. Nothing on screen will surprise you.

Presenter note

Start with the code this replaces, because everyone in the room has written it. It is a ladder of if (command.Contains("install")) ... else if (command.Contains("global")) ... that grows every sprint and is never quite right.

The Choice version states the answer space once, as three named options with descriptions, and the model has to pick one of them. The interesting part of the code moves out of the control flow and into the criteria text, which is where the judgment actually lives.

Then point at the two confidence numbers on the output line. You do not need to explain them fully yet, because step 12 does. The short version: the mock puts 0.76 of the probability on ask for a Medium-band state, so answer=0.76. The confidence=0.64 in front of it is the provider's own definition of the word, here Jev's (n×p_max - 1)/(n - 1). Run the same level with --provider laya and it reads 0.35, because Laya defines confidence as normalized entropy. Same distribution, same decision, different number. Policy in this repository only ever reads answer.

Make sure the 0.76 sticks. The mock puts 0.94 on the confident bands (Low and High) and 0.76 on Medium, so "the model is unsure" happens the same way on every run. At level 5, that 0.76 is exactly what fails the allow threshold.

Presenter note

Set this up with a question: when is a Choice the wrong tool? When the answers have an order. "Read-only" and "destructive" are different categories, but one is also clearly worse than the other, and a Score keeps that ordering.

Because the result is ordered, arithmetic on it means something. You can write "escalate above 2.0", or average the scores of the five files in a pull request. You cannot average a Choice.

Point at the 1.56. It is not a whole number, and that is useful: the action falls between "repository-local mutation" and "broad change", and the score says so instead of forcing it into one bucket.

Mention the legend that comes back with a Score, too. It maps each index back to its description, so a log line can say "1.56, between 'repository-local mutation with easy rollback' and 'broad change'" instead of a bare number that nobody can interpret six months later.

If someone asks where 1.56 comes from: the state mentions editing files and adding a package reference, which lands in the Medium band. The mock's normalized Medium value is 0.52, and 0.52 times (4 levels - 1) is 1.56.

Presenter note

This is where the first three levels come together: three question types, three answer types, and one request against one state.

Give two reasons that matters. Latency, because it is one round trip instead of three. Consistency, because all three judgments look at exactly the same evidence, so they cannot disagree just because one of them was sent a slightly different description.

The thresholds themselves are three lines of ordinary C#:

src/Jev.Core/CopilotToolGate.cs
// Gate on AnswerConfidence (max(p)), never on the provider's own `confidence` field: Jev
// reports (n*p_max - 1)/(n - 1) and Laya reports normalized entropy, so a threshold tuned
// against one provider would silently loosen or tighten against the other.
double confidence = answer.AnswerConfidence;

if (deny >= 0.55 || (answer.Choice.Equals("deny", OrdinalIgnoreCase) && confidence >= 0.60))
    return new GateResult(GateDecision.Deny, $"{ProviderName} classified the tool call as unsafe ...", confidence);

if (allow >= 0.85 && confidence >= 0.75)
    return new GateResult(GateDecision.Allow, $"{ProviderName} classified the tool call as low risk ...", confidence);

return new GateResult(GateDecision.Ask, $"{ProviderName} did not clear the confidence threshold ...", confidence);
Two lines here carry the entire provider story

answer.AnswerConfidence is max(p), which is normalized the same way across all three providers. answer.Confidence - the field that arrives on the wire and looks like the obvious one to read - is not comparable across providers and appears nowhere in this file. ProviderName is the only other provider-aware thing in the gate, and it only affects the human-readable reason string, which is why the same run under Laya reads "Laya did not clear the confidence threshold".

Presenter note

Slow down here. Level 5 is where the talk turns from "look what the model can tell you" to "here is who gets to decide". CopilotToolGate, the class it introduces, is the same one that levels 8, 9, and the real hook use later.

Run it and read the three output lines. Then walk through the middle row out loud, with the numbers. It is the most convincing minute of the demo.

dotnet add package Example.Package lands in the mock's Medium band. The Choice comes back as ask, and the distribution is deny 0.12, ask 0.76, allow 0.12. Now apply the code. Deny at 0.12 is below the 0.55 deny bar, so no deny. Allow at 0.12 is nowhere near the 0.85 allow bar, so no allow. It falls through to ask. At no point did the code look up what the model chose and simply do that.

Next, point out that the thresholds are lopsided: 0.55 to deny, 0.85 to allow. A wrong deny is cheap, because the developer can run the command themselves. A wrong allow is expensive, because the command has already run. Any pair of thresholds encodes some view of those costs, and this pair states it openly.

Last, the read-only fast path, which is there for speed and privacy. An agent session makes dozens of view and grep calls. Sending each one to a remote model would add latency to every read and send your repository paths to an external API, without changing a single decision.

Why anchored regexes and not substring matching

The deterministic layer lives in RiskHeuristics.cs. Substring matching is wrong in both directions, which is why every rule is an anchored regex:

dotnet test --filter Rebootdenied matched "reboot"ask
grep -rn OnShutdownAsync srcdenied matched "shutdown"allow read-only

Before you start the session, give them three facts about how hooks fail. They apply to anyone building an agent hook, whatever their stack.

1. A crash or non-zero exit fails closed. Copilot treats it as deny. That sounds safe, and it is, but it is miserable in practice: every tool call in the session is denied and the user has no idea why. That is why the Windows hook entry keeps -ExecutionPolicy Bypass -File. A default Windows execution policy refuses to load an unsigned .ps1, PowerShell exits non-zero, and the session becomes unusable without a word of explanation. Both wrapper scripts always exit 0 and print a decision, even when they cannot do their job.

2. A hook timeout fails open. Copilot falls back to its normal permission flow. This is the one failure that can let something through, so the adapter does not rely on the outer timeout at all. It starts its own CancellationTokenSource covering both reading stdin and the whole gate evaluation, and turns expiry into an explicit ask. The timeouts nest on purpose: 2s live HTTP cap < 4s DECISION_HOOK_DEADLINE_MS < 8s timeoutSec. Change one and you need to change the others.

3. Under Copilot's cloud agent there is nobody to answer ask, so ask is treated as deny. People tend to assume the unattended path is the risky one. Here it works the other way: a policy tuned for interactive use gets stricter in the cloud, never looser.

It is tempting to scroll past a compose file. Stop at the sandboxing block instead. An organization usually wants a local engine because tool arguments must not leave the machine. Production hardening

This repository optimizes for readability. Before promoting the pattern to organizational policy, work through this list:

Parsing

Replace regexes with real shell and command-line parsing. Regexes cannot follow rm $VAR, base64 payloads, or creative quoting.

Secrets

Add dedicated secret detection and redaction before any external model call. LooksSensitive is a shape matcher, not a scanner.

Distribution

Sign and version the policy. A repository hook is only as trustworthy as the repository, and hooks execute as the local user.

Observability

Add audit logging of every decision plus latency and error telemetry. You cannot tune thresholds you cannot measure.

Enforcement

Use enterprise policy hooks or sandboxing where a repository-level hook is not a strong enough boundary, particularly for the fail-open timeout path.

Accuracy

Fine-tune on your own decisions. The shipped Laya checkpoints are zero-shot, and upstream reports 0.362 for the base English checkpoint against 0.766 for typed-decisions on its own benchmark. Re-validate every threshold on your own traffic.

Test corpus

Derive policy tests from real tool traces, not from imagination. The ten samples here are a starting shape, not a sufficient corpus.

The question to answer first

Decide whether a remote model call is permitted at all for the data being evaluated. Tool arguments routinely contain source code, file paths, and repository structure. For some organizations the correct deployment is DECISION_MODE=off with the deterministic layers only; for others it is a self-hosted Laya container, where the state never leaves the machine.

Presenter note

This is a good place to close, and the honest ending is the stronger one. This is a teaching repository, and the README says so in its first line. What carries over to production is four design decisions rather than the code itself.

  1. Layer order. Deterministic rules run before the model, every time. The model gets the ambiguous middle and nothing else.
  2. Ownership. Thresholds are C# literals in version control, reviewed in pull requests, not prose inside a prompt.
  3. Failure direction. Every degraded path ends at "ask a person", and the one failure that fails open is covered by an inner deadline instead of being trusted.
  4. Tests in both directions. Every rule has a command that must match and a harmless one that must not, so loosening a rule shows up in a diff.

All four hold whether you use Jev, Laya, Decider, a different model, or no model at all. The provider switch is itself an example of the second one: provider differences are data in SystemOneEndpoint, not branches in the policy code.
