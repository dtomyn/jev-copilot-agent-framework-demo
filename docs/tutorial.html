The mental model: Jev advises, code authorizes

Jev (the TypeSafe "System One" API) answers bounded semantic questions very fast: a yes/no probability, a one-of-N choice, or a position on an ordered rubric. It is deliberately not a planner and not a code generator.

This repository takes that primitive and walks it up ten levels until it is sitting inside a real GitHub Copilot CLI preToolUse hook, deciding whether the coding agent's next tool call should run. One idea holds the whole progression together:

Jev advises; code authorizes.

Jev never returns an authorization. It returns evidence: a number and a confidence. Deterministic C# owns the hard rules, owns the thresholds, and owns the final allow ask deny.

Presenter note

This framing is the reason the demo is worth giving at all. The naive version of an "AI safety hook" is model says safe, therefore execute. That fails in two directions at once: it is bypassable through prompt injection inside the tool arguments, and it is unauditable because the policy lives in a prompt rather than in reviewable code.

The version here inverts the relationship. Before Jev is consulted at all, an anchored regex layer hard-denies the commands nobody needs a model to judge, and a credential layer stops secret-shaped text from ever leaving the machine. Jev only sees the ambiguous middle, and even then the C# code decides what its numbers are allowed to mean.

A useful contrast to draw out loud: the deterministic layer has a knowable, testable false-negative rate; the model layer has an unknown one. So the deterministic layer is placed where a false negative would be fatal, and Jev is placed where the worst case is one unnecessary human prompt.

Presenter note

Two build invariants are worth knowing before anyone tries this on their own machine, because both produce confusing failures.

NuGet feeds. NuGet.config clears all sources and pins exactly one (nuget.org), and the repo uses Central Package Management. If a machine-level or corporate feed leaks in, NuGet raises NU1507 ("there are N package sources defined"), and because Directory.Build.props sets TreatWarningsAsErrors, that warning becomes a build break. The fix is not to relax the warning; it is to keep the pin or add explicit package source mapping.

The npm download. TenLevels.Jev depends on GitHub.Copilot.SDK transitively, and its MSBuild targets download the Copilot CLI from registry.npmjs.org at build time. That is the only step in this repository that needs a non-NuGet network endpoint. The repo caps that download at 90 seconds (CopilotCliDownloadTimeout) instead of the SDK default of 600, precisely so a blocked corporate network gives you an error in a minute and a half rather than a ten-minute silent hang.

Building the hook is not optional

The Copilot hook wrapper executes a pre-built DLL. It never restores or builds inside the hook. If src/Jev.CopilotHook/bin/Release/net10.0/Jev.CopilotHook.dll is missing, the wrapper deliberately returns ask for every tool call with the reason "Jev hook is not built."

Presenter note

The ordering here is the whole point, and it is worth one sentence on stage. Everything that can be built and verified offline is built and verified first. The one project that needs an internet resource outside NuGet is built last, and its failure is reported as a warning rather than aborting the script. So a restricted-network attendee still ends up with a working hook, working self-tests, and eight runnable levels.

The "no build inside the hook" rule deserves emphasis too. A preToolUse hook runs on every single tool call in a Copilot session, inside an 8-second timeout. A cold dotnet build there would blow the timeout, and a hook timeout in Copilot CLI fails open. So the design choice "compile ahead of time, execute a DLL" is a security property, not just a speed optimization.

Notice also what the wrapper does when the DLL is missing: it returns ask, not allow and not a crash. Every degraded path in this repo lands on "ask a human."

2The three Jev primitives and the wire format

Before running anything, look at the shape of a Jev request. One state, one model, and a named dictionary of typed questions. You can ask several questions of different types about the same state in a single round trip.

POST https://api.typesafe.ai/v1/systemone
{
  "state": "Copilot wants to update a package and regenerate snapshots.",
  "model": "jev-latest",
  "questions": {
    "side_effect": {
      "type": "noul",
      "instructions": "Does this have persistent side effects?"
    },
    "route": {
      "type": "choice",
      "instructions": "How should this be handled?",
      "criteria": {
        "allow": "Low-risk and reversible",
        "ask":   "Consequential or ambiguous",
        "deny":  "Clearly prohibited"
      }
    },
    "risk": {
      "type": "score",
      "instructions": "Rate operational risk",
      "criteria": ["read-only", "small mutation", "broad mutation", "destructive"]
    }
  }
}
PrimitiveQuestion shapeAnswer shapeUse it when
Noul One yes/no proposition, optional true / false criteria noul: probability 0.0 to 1.0 The answer is a single proposition and you want a threshold in code
Choice A named set of options, each with a description choice, confidence, full probabilities map The complete answer space can be written down in advance
Score An ordered array of descriptive levels, index 0 upward score, confidence, legend, probabilities The answer is a position on a rubric, not a category

In C# these map to records in src/Jev.Core/Models.cs, with a polymorphic type discriminator:

src/Jev.Core/Models.cs
[JsonPolymorphic(TypeDiscriminatorPropertyName = "type")]
[JsonDerivedType(typeof(NoulQuestion),   "noul")]
[JsonDerivedType(typeof(ChoiceQuestion), "choice")]
[JsonDerivedType(typeof(ScoreQuestion),  "score")]
public abstract record JevQuestion;

Every implementation talks to one interface, which is what makes the mock and the live client interchangeable everywhere in the repo:

src/Jev.Core/IJevClient.cs
public interface IJevClient
{
    Task<SystemOneResponse> DecideAsync(
        object state,
        IReadOnlyDictionary<string, JevQuestion> questions,
        CancellationToken cancellationToken = default);
}
Presenter note

Three things to point at in this section.

Why "bounded" matters. The reason a Score takes an ordered array of descriptive levels rather than "rate 1 to 10" is that a bare 1-to-10 scale has no shared meaning between the caller and the model. Writing out "read-only / small repository-local mutation / broad or stateful mutation / destructive or security-sensitive" makes the rubric reviewable in a pull request. Someone can disagree with level 2's wording in code review. Nobody can meaningfully code-review "rate it 1 to 10."

Why the whole probability distribution is returned. The Choice answer carries every option's probability, not only the winner. CopilotToolGate uses that: it reads probabilities["deny"] directly rather than trusting the argmax. A 0.45 / 0.45 / 0.10 split has a winner, but it is a coin flip, and code that only looks at choice cannot tell the difference between that and a 0.95 landslide.

Why the interface is this small. One method, one state, a dictionary of questions. That is what lets MockJevClient and JevHttpClient be swapped by a single CLI flag, and it is why the self-tests can assert the exact serialized wire shape against a stub HttpMessageHandler without any network.

Level 01 - the smart if-statement

src/TenLevels.Jev/Levels/Level01SmartIf.cs
const string state = "Copilot proposes: rm -rf ./artifacts after the build.";

var response = await jev.DecideAsync(state, new Dictionary<string, JevQuestion>
{
    ["dangerous"] = new NoulQuestion(
        "Is this proposed coding-agent action potentially destructive?",
        new NoulCriteria(
            "Could delete important files or make an irreversible change.",
            "Read-only or clearly reversible.")),
});

var answer = (NoulAnswer)response.Answers["dangerous"];
Console.WriteLine(answer.Noul >= 0.80 ? "C# policy: BLOCK" : "C# policy: continue normal checks");
Presenter note

The whole lesson of level 1 is the last line. The threshold 0.80 is a literal in your source file. It shows up in a diff, it can carry a comment explaining why it is 0.80 and not 0.65, and it can be changed without touching a prompt. Jev supplied a number; your code supplied the meaning.

Mention the NoulCriteria pair as well. Spelling out what "true" means and what "false" means is what turns a vague question into a bounded one. Without it you are relying on the model and the reader agreeing about the word "destructive."

If someone asks why the mock returns exactly 0.94: the state contains rm -rf, which matches a hard-deny regex, so RiskHeuristics.Classify puts it in the High band, and the mock maps High to 0.94 every time. Determinism is the feature. Your demo output will never surprise you.

Level 02 - typed routing

output
=== Level 02: Typed routing ===
Replace a pile of fuzzy conditionals with a bounded Choice.

route: choice=ask, confidence=0.76

The state is "Copilot proposes to install a new global CLI package and update PATH." The answer space is written out in advance as three named options with descriptions, so the model cannot invent a fourth.

Presenter note

Contrast this explicitly with the code it replaces. The hand-written version is a ladder of if (command.Contains("install")) ... else if (command.Contains("global")) ... that nobody can keep correct as the surface grows. The Choice version states the answer space once, and the interesting part becomes the criteria text rather than the control flow.

The confidence of 0.76 is not a rounding artifact. The mock returns 0.94 for confident bands (Low and High) and 0.76 for the Medium band, so "the model is unsure" is reproducible on stage. You will use that 0.76 again at level 5, where it is exactly what fails the allow threshold.

Level 03 - ordered risk

output
=== Level 03: Ordered risk ===
Use a Score when the answer is an ordered rubric rather than a category.

risk: score=1.56, confidence=0.73

The rubric has four descriptive levels, so valid scores run from 0.0 to 3.0:

rubric
0  Read-only or trivial reversible action.
1  Repository-local mutation with easy rollback.
2  Broad change that affects dependencies, generated assets, or repository state.
3  Destructive, system-wide, credential-sensitive, or difficult to reverse.
Presenter note

The key difference from Choice: a Score is ordered, so arithmetic on it is meaningful. You can say "escalate above 2.0" or "average the scores of the five files in this PR." You cannot average a Choice.

Where 1.56 comes from, if asked: the state mentions editing files and adding a package reference, which lands in the Medium band, the mock's normalized Medium value is 0.52, and 0.52 multiplied by (4 levels - 1) is 1.56. The non-integer result is the point. The action sits between "repository-local mutation" and "broad change," and the score preserves that rather than forcing it into a bucket.

Note also that a Score answer returns a legend, mapping each index back to its description. That is what lets a log line say "1.56, between 'repository-local mutation with easy rollback' and 'broad change'" instead of a bare number nobody can interpret six months later.

Level 04 - parallel typed judgments

output
=== Level 04: Parallel typed judgments ===
Ask Noul, Choice, and Score questions together against one state.

has_side_effect: noul=0.58
route: choice=ask, confidence=0.76
risk: score=1.56, confidence=0.73
model=mock-jev, input_tokens=20
Presenter note

Three different question types, three different answer types, one request and one state. This matters for two practical reasons: latency (one round trip instead of three) and coherence (all three judgments are made against exactly the same evidence, so they cannot disagree because one of them saw a different description).

The input_tokens line is worth a beat. Jev is priced and budgeted like any other model call, and a hook that runs on every tool call in a long agent session makes that cost real. The usage block is surfaced in the demo output specifically so nobody forgets there is a meter running.

Design guidance to offer here: prefer one request with several named questions over several requests. Name the questions after what you will do with the answer (has_side_effect, route, risk), not after the model.

This is the hinge of the whole tutorial. Level 5 introduces CopilotToolGate, the class that levels 8, 9, and the real Copilot hook all reuse unchanged.

The layer order

1
Deterministic hard denyAnchored regexes for explicitly destructive commands. Returns deny. Jev is never called.
2
Credential stopAnything that looks like secret material returns ask and is never forwarded to an external API.
3
Read-only fast pathKnown non-mutating tool names return allow with no model call and no latency.
4
Host Jev tool exemptionjev_noul, jev_choice, jev_score return a judgment and cannot mutate anything.
5
Jev semantic classificationThe ambiguous middle becomes a bounded Choice over allow / ask / deny.
6
Code-owned thresholdsC# literals turn probability and confidence into a decision.
7
Default: ask a humanEverything that did not clear a threshold escalates. Ask is the fallback, never allow.

The thresholds themselves are three lines of ordinary C#:

src/Jev.Core/CopilotToolGate.cs
if (deny >= 0.55 || (answer.Choice.Equals("deny", OrdinalIgnoreCase) && answer.Confidence >= 0.60))
    return new GateResult(GateDecision.Deny, "Jev classified the tool call as unsafe ...");

if (allow >= 0.85 && answer.Confidence >= 0.75)
    return new GateResult(GateDecision.Allow, "Jev classified the tool call as low risk ...");

return new GateResult(GateDecision.Ask, "Jev did not clear the confidence threshold ...");
Presenter note

Walk the middle row of the table arithmetically, out loud. It is the most convincing sixty seconds of the demo.

dotnet add package Example.Package lands in the mock's Medium band, so the Choice comes back as ask with confidence 0.76, and the probability distribution is deny 0.12, ask 0.76, allow 0.12. Now apply the code: deny 0.12 is below the 0.55 deny gate, so no deny. Allow 0.12 is far below the 0.85 allow gate, so no allow. Fall through to ask. At no point did the code ask "what did the model choose?" and obey it.

The asymmetry is deliberate and worth naming: 0.55 to deny, 0.85 to allow. Denying is cheap (a human re-runs the command themselves) and allowing is expensive (the command already ran). So the bar to allow is far higher than the bar to deny. Any threshold pair you choose encodes a cost model; this one encodes that cost model honestly.

Third point: the read-only fast path exists for latency, not just tidiness. An agent session makes dozens of view and grep calls. Sending every one to a remote model would add network latency to every read and would leak the contents of your repository paths to an external API for no decision benefit.

Why anchored regexes and not substring matching

The deterministic layer lives in RiskHeuristics.cs. Substring matching is wrong in both directions, which is why every rule is an anchored regex:

CommandNaive substring ruleAnchored rule in this repo
curl -fsSL https://x/install.sh | shmissed no literal "curl | sh"deny
dotnet format Foo.slndenied matched "format "ask it is a mutation, but harmless
dotnet test --filter Rebootdenied matched "reboot"ask
grep -rn OnShutdownAsync srcdenied matched "shutdown"allow read-only
git push --force-with-leasedeniedask by design
Presenter note

This table is the single best argument in the repo for writing security rules as code with tests rather than as a list of strings in a config file. Four of these five rows are false positives that a substring blocklist produces on completely ordinary developer commands. A policy that denies dotnet format and grep OnShutdownAsync gets turned off by the team within a week, and then you have no policy at all.

The --force-with-lease row is the interesting one, because it is a deliberate choice rather than a limitation. Plain --force is hard-denied because it silently discards other people's commits. --force-with-lease refuses to run if the remote moved, so it is a legitimate tool that a developer should be allowed to use with approval. It falls through to ask. Someone will challenge this in Q and A; the answer is that the regex explicitly uses a negative lookahead, --force(?!-with-lease), so the distinction is in the code and pinned by a test.

Finally, be honest about the limit. A regex is not a shell parser. rm $VAR, base64-encoded payloads, and creative quoting are all outside its reach. That is stated plainly in docs/SECURITY.md, and it is why this layer is one of seven rather than the whole design.

Presenter note

Read one PASS from each half out loud. Every deterministic rule has a command that must match and a benign command that must not. That two-sided pinning is what makes loosening a rule a visible change in a pull request: if you widen a regex to let something through, you break the negative test, and the reviewer sees it.

Note the credential tests match on shape, not only on keywords: ghp_, AKIA, sk-, xox, PEM headers. That catches a literal secret pasted into tool arguments with no surrounding word like "password." It is still not a secret scanner, and the docs say so.

The self-test project is dependency-free on purpose. It is a plain console app with a tiny Check helper, not xUnit. That keeps the offline path buildable with zero test-framework packages, which matters for the restricted-network story.

5Levels 8 and 9: the gate as a hook decision

Presenter note

The most interesting demonstration in this section is not in the default output. Run the same edit tool twice with different semantic content and show that the decision changes:

  • edit with "change":"replace retry policy" gives ask at confidence 0.76.
  • edit with "change":"update authentication middleware" gives deny at confidence 0.94, and critically the reason is not "Deterministic policy ..." It came from Jev.

That is the payoff for the whole first half of the talk. Same tool, same file, no regex matched, and the decision differs because of what the change means. That is exactly the class of judgment a regex cannot make and a full planning LLM is too slow and too unbounded to make on every tool call.

There is a self-test asserting precisely this, named "semantic high risk is still Jev-governed, not hard-denied," which additionally asserts that the reason string does not start with "Deterministic policy." That is a test of the explanation, not just the decision, and it is worth calling out as a pattern: if your policy engine returns reasons to humans, test the reasons.

Presenter note

Point out that four of these nine samples are regression cases. They exist because an earlier, more naive version of the rule got them wrong. Each sample file even carries a note field explaining the mistake it prevents. That is a good pattern to copy wholesale: a policy corpus where each case documents the bug it was born from.

The last two rows are the subtlest pair in the repo and reward slowing down.

jev-tool must be allow because of an interaction most people do not anticipate: the Copilot runtime that Microsoft Agent Framework spawns runs in this repository's working directory, so it loads this repository's .github/hooks/jev-policy.json too. That means the hook sees the jev_noul / jev_choice / jev_score functions that the host itself registered. Without the narrow exemption in the gate, the repository's own hook denies the agent's own Jev calls and levels 6, 7, and 10 fail with a fail-closed hook error.

jev-tool-with-secret is the guard on that exemption. Its payload carries Authorization: Bearer abc123 inside the Jev call's own state argument. Because the credential layer runs before the exemption, it still returns ask and the secret is never forwarded. Ordering inside the gate is load-bearing, and this sample is what stops someone from reordering it during a refactor.

Choose the mode before starting Copilot

Repository hook configuration and the environment are read when the CLI starts. Changing JEV_MODE inside a running session has no effect. Set it, then launch.

Presenter note

There are three failure-semantics facts in this section, and they are the most transferable content in the entire repository. Anyone building an agent hook needs all three.

1. A crash or non-zero exit fails closed. Copilot treats it as deny. Sounds safe, and it is, but the failure mode is brutal: every tool call in the session is denied and the user has no idea why. This is exactly why the Windows hook entry keeps -ExecutionPolicy Bypass -File. A default Windows execution policy refuses to load an unsigned .ps1, PowerShell exits non-zero, and the session silently becomes unusable. Both wrapper scripts therefore always exit 0 and print a decision object even when they cannot do their job.

2. A hook timeout fails OPEN. Copilot falls back to its normal permission flow. This is the one failure mode that can let something through, so the adapter refuses to depend on the outer timeout at all. It starts its own CancellationTokenSource covering stdin reading and the entire gate evaluation, and converts expiry into an explicit ask. The nesting is deliberate: 2s live HTTP cap < 4s JEV_HOOK_DEADLINE_MS < 8s timeoutSec. If you change one number, change the others.

3. Under Copilot's cloud agent there is nobody to answer ask, so ask is treated as deny. The pleasant consequence is that a policy tuned for interactive use is strictly more restrictive in the cloud, never less. Worth stating explicitly, because the instinct is to assume the unattended path is the risky one.

If you want one live moment that sells the whole design: run the session, ask Copilot to force push, and let the audience watch the deny come back in a few milliseconds with a human-readable reason. Then point out that no model was consulted for that decision.

The hook contract, precisely

stdin -> the hook
{
  "sessionId": "demo",
  "timestamp": 0,
  "cwd": ".",
  "toolName": "bash",
  "toolArgs": { "command": "git push --force origin main" }
}
stdout <- the hook (exactly one object, exit 0)
{"permissionDecision":"deny","permissionDecisionReason":"Deterministic policy matched a destructive command pattern."}
Presenter note

"Exactly one JSON object" is not stylistic advice. Two objects printed back to back concatenate into invalid JSON and the whole decision is discarded. The adapter has a single Emit helper and every code path calls it exactly once, including both catch blocks.

Also note NormalizeToolName in Program.cs. Different agent CLIs name the same primitives differently (read vs view, shell vs bash, str_replace vs edit). Normalizing at the boundary is what keeps the read-only fast path meaningful across hosts, and it means porting this hook to another agent runtime is mostly a matter of extending one switch expression.

Finally: the reason string is part of the contract, not decoration. It is what the developer sees when their command is blocked. A policy that says "denied" with no reason gets disabled; one that says "deterministic policy matched a destructive command pattern" gets understood.

8Levels 6 and 7: Jev as Agent Framework function tools

These levels need an authenticated GitHub Copilot CLI. They host Copilot as a Microsoft Agent Framework AIAgent and hand it Jev as ordinary function tools.

command
dotnet run --project src/TenLevels.Jev -- --level 6 --jev mock
dotnet run --project src/TenLevels.Jev -- --level 7 --jev mock
src/TenLevels.Jev/Copilot/JevToolSet.cs
public IList<AIFunctionDeclaration> AllTools() =>
[
    AIFunctionFactory.Create(NoulAsync,   "jev_noul",   "Ask Jev a bounded yes/no question and receive a probability from 0 to 1."),
    AIFunctionFactory.Create(ChoiceAsync, "jev_choice", "Ask Jev to choose one item from a bounded list and receive probabilities/confidence."),
    AIFunctionFactory.Create(ScoreAsync,  "jev_score",  "Ask Jev to rate state against an ordered list of descriptive levels."),
];

Level 6 gives the agent only jev_noul. Level 7 gives it all three and asks it to compose them. Neither level grants the agent shell, file, or URL permissions.

These agents get no execution tools on purpose

The Agent Framework levels demonstrate decision composition. Granting them Copilot's built-in shell and file permissions would create a second, hidden execution-policy surface next to the hook, which would muddy exactly the lesson the repo is trying to teach.

Presenter note

The contrast between level 5 and level 6 is the one to draw here, because it is a genuine architectural fork rather than an incremental step.

In level 5 your code decided when to consult Jev. In level 6 the agent decides, because Jev is now a tool declaration in its context window. You have traded determinism for flexibility. Both are legitimate; they answer different questions. Use the tool form when the agent is doing the reasoning and needs a bounded sub-judgment. Use the gate form when you are enforcing policy, because policy must not be optional.

Level 7's prompt asks the agent to both classify (Choice) and score (Score) the same task, which shows composition. The system instructions explicitly tell it to use ordinary reasoning for arithmetic and deterministic facts. That guardrail is important: the failure mode of giving a model a "decide" tool is that it starts routing everything through it, including questions it could answer exactly.

One operational note worth saying while it runs: the first invocation is slow because the Copilot runtime has to start. If it fails, the level runner catches the exception and prints "Level N needs a working, authenticated GitHub Copilot runtime," rather than dumping a stack trace. With --all --include-agent it records a non-zero exit code and keeps going.

The CLI-native equivalent

The same behaviour is taught to plain copilot sessions by two checked-in files.

Agent skill

.github/skills/jev-decisions/SKILL.md. Copilot can select it automatically when a task matches its description, or you can request it explicitly with /jev-decisions.

Custom agent

.github/agents/jev-engineer.agent.md. Select it in-session with /agent, or launch it directly from the command line.

command
copilot --agent=jev-engineer --prompt "Review this change and use Jev only if a bounded semantic decision would help."

The skill's guardrails are the distilled version of everything above:

  1. Prefer deterministic inspection, tests, parsers, compilers, linters, and arithmetic over Jev whenever they can answer the question directly.
  2. Keep the input state limited to evidence relevant to the judgment. Never send secrets.
  3. Do not ask Jev to write code, execute commands, invent policy, or make open-ended plans.
  4. The caller owns thresholds and policy. Jev is evidence, not authorization.
  5. Preserve uncertainty. Below the threshold, escalate to a person.
  6. The repository preToolUse hook remains authoritative and must not be bypassed.
Presenter note

Level 10 is the only level where "the agent chose not to use the tool" is a passing result. Say that before you run it, so the audience is watching for the right thing. A test-suite scoping question is partly deterministic (the compiler and the reference graph know who touches that property), so an agent that answers "I can determine this by inspection" has understood the lesson better than one that reflexively calls jev_score.

Note the division of labour between the two files, because people conflate them. The skill is knowledge: when this primitive is appropriate and how to shape the question. The custom agent is a persona plus tool configuration. The skill is reusable by any agent; the agent profile is repository-specific.

Worth calling out explicitly: jev-engineer.agent.md declares tools: ["*"] but that is not a security hole, and explaining why demonstrates that the layering actually works. The agent profile grants tool availability; the preToolUse hook still sits in the normal lifecycle and still gates every call. Capability and authorization are separate concerns, and this repo keeps them in separate files. The agent profile even instructs the agent not to edit around or disable the hook, and copilot-instructions.md repeats that at the repository level.

Everything above ran against the deterministic mock. Swapping in the real API is one environment variable and one flag.

Windows PowerShell

macOS / Linux bash

For the hook, set the mode as well, before launching Copilot:

Windows PowerShell
$env:JEV_MODE = "live"
$env:TYPESAFE_API_KEY = "..."
copilot
Timeouts differ between the two callers

The CLI levels use a 15-second HTTP timeout. The hook constructs its client with a hard 2-second cap, because it is on the critical path of every tool call and must return before the 4-second internal deadline.

Presenter note

Two things change the moment you go live, and both are worth naming before someone discovers them in production.

Determinism disappears. The mock returns 0.94 for High every single time. A real model does not. Run level 4 twice in live mode and the numbers move. This is why the thresholds in CopilotToolGate have margin built in rather than sitting at 0.50, and it is why the same ambiguous command can produce ask on one run and allow on the next if you set the bar too close to the noise floor.

Your tool arguments leave the machine. That is precisely what the credential layer is defending against, and it is also the question to put to any organization adopting this pattern: is a remote model call permitted for the data being evaluated at all? For some repositories the honest answer is no, and JEV_MODE=off plus the deterministic layers is the correct deployment. The repo supports that mode as a first-class option rather than a degraded one.

JEV_MODE=auto is the pragmatic middle for shared configuration: live when a key is present, off when it is not, and never an accidental hard failure because someone cloned the repo without a key.

Presenter note

Rows three and four are the two failure modes that deserve a live rehearsal before any demo, because they are indistinguishable from "the demo is broken" and they fail in opposite directions.

If the hook exits non-zero, Copilot denies everything and the session appears to be catatonic. If the hook is simply unbuilt, every call becomes an approval prompt and the session appears to be paranoid. Both look like the tool is broken rather than the setup being wrong. Pipe one sample payload through the wrapper before you present, and you will know in two seconds which world you are in.

Production hardening

This repository optimizes for readability. Before promoting the pattern to organizational policy, work through this list:

Parsing

Replace regexes with real shell and command-line parsing. Regexes cannot follow rm $VAR, base64 payloads, or creative quoting.

Secrets

Add dedicated secret detection and redaction before any external model call. LooksSensitive is a shape matcher, not a scanner.

Distribution

Sign and version the policy. A repository hook is only as trustworthy as the repository, and hooks execute as the local user.

Observability

Add audit logging of every decision plus latency and error telemetry. You cannot tune thresholds you cannot measure.

Enforcement

Use enterprise policy hooks or sandboxing where a repository-level hook is not a strong enough boundary, particularly for the fail-open timeout path.

Test corpus

Derive policy tests from real tool traces, not from imagination. The nine samples here are a starting shape, not a sufficient corpus.

The question to answer first

Decide whether a remote Jev call is permitted at all for the data being evaluated. Tool arguments routinely contain source code, file paths, and repository structure. For some organizations the correct deployment is JEV_MODE=off with the deterministic layers only.

Presenter note

Close on the honest version, because credibility is worth more than a clean ending: this is a teaching repository and the README says so in the first line. What transfers to production is not the code, it is the four structural decisions.

  1. Layer order: deterministic rules before the model, always. The model gets the ambiguous middle and nothing else.
  2. Ownership: thresholds are C# literals in version control, reviewed in pull requests, not prose inside a prompt.
  3. Failure direction: every degraded path lands on "ask a human," and the one failure mode that fails open is defended against by an inner deadline rather than trusted.
  4. Two-sided tests: every rule has a command that must match and a benign command that must not, so loosening a rule is visible in a diff.

Those four hold regardless of whether you use Jev, a different model, or no model at all.
